# 1. Purpose

UI-020, UI-021 and UI-023 are **not three destinations**. They are three views of
**one object at three stages of maturity**: an automation asset expressed as
behaviour, as code, and as a decision.

Building them as three separately navigated screens would reproduce the exact
defect reported against the already-delivered screens — too many steps, unclear
what is happening. This contract therefore specifies **one workspace with three
tabs** over a single suite member, while keeping each screen a distinct,
addressable, separately acceptance-testable route so the tracker rows for
UI-020, UI-021 and UI-023 close honestly.

The workspace has a second purpose of equal weight: it is where the platform's
declared operating model finally becomes real.

> `agent work -> deterministic validation -> automatic stage advancement -> human approval only at governed gates`
> — `CLAUDE_CODE_HANDOVER.md` line 69
>
> "Routine advancement should become automatic after successful deterministic
> validation; manual transitions are fallback controls." — line 261

Today every advancement in the automation module is manual. This contract
introduces the **Autonomy and Scoring Model** (Section 14) that makes routine
advancement automatic, and confines human effort to one governed gate.

## 2.1.2 Divergence 1 — the JSON in UI-020 is not the real schema

**This is the most consequential finding in the reconciliation.**

The image's JSON shows `step_mappings[]` containing `step_key`, `intent`,
`target`, `data`, `confidence`, `dependencies`, `alternatives`, `notes`, with
assertions of type `url_contains`, a `target` expressed as an array of
`{locator, value_ref}` objects, and top-level `version` / `ir_draft_id`.

The real `AutomationGenerationContract` (`app/agents/automation/generation_contract.py`)
has none of that shape:

| Image | Reality |
|---|---|
| `step_mappings[]` | `steps[]`, plus a separate `pageObjects[]` |
| `intent` | `action`, from a closed `StepAction` vocabulary |
| `"intent": "set_values"` | not a member of `StepAction` |
| `"type": "url_contains"` | `AssertionType` is `visible` \| `text` \| `url` \| `value` \| `count` |
| `target: [{locator, value_ref}]` | `target` is a **string**, `"<PageObject>.<element>"` |
| `data: {}` | `dataBinding` (a name into `testDataBindings`) |
| per-step `confidence` / `dependencies` / `alternatives` | do not exist |
| `version` / `ir_draft_id` | `contractVersion` / `testCaseId` |

**Resolution: the image's JSON is illustrative. The real schema is
authoritative.** Implementing the drawn shape would create a second IR format
alongside the one the compiler consumes, which is exactly the class of decision
that caused the four previous rebuilds. The visual design of the panel is
adopted unchanged; its contents render the real contract.

The mock's per-step `confidence: 0.92` has no source in the IR. Where a
confidence figure is shown against a step, it is derived from the real
`LocatorMapEntry.confidence_score` of the referenced element, or omitted —
never invented (repository rule 6).

## 2.1.3 Divergence 2 — IR editing surface

The image makes a raw JSON editor the primary editing surface. That reintroduces
the complexity the delivered screens were rejected for, and makes
`_targets_resolve_to_real_elements` violations trivially easy to type.

**Resolution (user decision):** structured form is the default; JSON moves
behind an **Advanced** toggle. The panel's frame is unchanged — same card, same
`Validate` and `Format` actions, same expand control, same footer with schema
badge and `Save IR`. Only the body's default rendering changes. See Section 11.4.

## 2.1.4 Divergence 3 — the gating rule as drawn is unsafe

The image's gate reads *"Score ≥ 70 and no critical issues"* → *"Automatically
eligible for Submit"*. Two conditions only. Its own "Real execution — 3 passed"
card sits beside the gate but is **not** one of them.

This is precisely the defect documented in Section 14.3: an asset that has never
been executed reaches ~0.70 on the scoring service's neutral defaults alone, so
a score-plus-criticals gate systematically favours the least-evidenced assets.

**Resolution (user decision):** the five hard preconditions of Section 14.2
govern, with the threshold applied after them. The panel keeps the image's
layout; the precondition list is rendered beneath the verdict.

**Threshold value remains open.** The image says 70, this contract says 80, and
the original discussion said "75 or 80". Section 30 carries it as the one
unresolved number.

## 2.1.5 Divergence 4 — autonomy strength and the single-axis stepper

As drawn, AI approval confers *eligibility to submit* and a human still clicks
Submit on every asset — leaving exactly the per-asset click the complexity
feedback targets. Separately, the approval stepper is a **single axis**, so
`AI_APPROVED` has nowhere to sit without colliding with the human record and
recreating the separation-of-duty problem of Section 14.1.

**Resolution (user decision):** automatic advancement with deferred Final
Approval. The stepper is retained exactly as drawn — it mirrors `lifecycle.py`
and is the human axis. The machine axis is added **above** it as the autonomy
badge and lane. The two are never the same field.

## 2.1.6 Divergence 5 — Language / Framework is editable in UI-021

The image renders `Language / Framework` as a dropdown. Framework is inherited
from the suite (Section 5, rule 4), and re-entering it here can contradict
UI-018's `MULTIPLE_FRAMEWORKS` conflict detection. The drawn value
"Python / Playwright" is also not a real `ScriptType` — the values are
`playwright-typescript` and `pytest-python`.

**Resolution:** rendered **read-only with its inheritance source label**, in the
dropdown's visual position, showing the real `ScriptType`. Changing framework
remains a suite-level action in UI-018, where conflict detection can respond to
it. `Entry file` stays a real selector over the compiled bundle.

## 2.1.7 Divergence 6 — the compiled file tree

The image shows nine files including `conftest.py`, `pytest.ini`,
`requirements.txt`, `README.md`, `locators/` and `data/users.json`. The compiler
emits `specs/`, `pages/`, `fixtures/testData.fixture.ts` and
`utils/{apiClient,dbValidator,evidenceHelper}.ts` for Playwright, and the
corresponding pytest bundle — not the mock's scaffold.

**Resolution (user decision):** render the real compiler output. The tree will
have fewer nodes than the image. A fuller runnable-project scaffold is recorded
as a tracker follow-up, not built in this pass.

## 2.1.8 Divergence 7 — where execution is triggered

v1.0 placed the dry run in the Script tab. The images place `Run validation` in
Validation & Review and show no run control on Script.

**Resolution:** the images are followed. `Run validation` in Tab C is the single
deterministic pass — static gate, execution and scoring together — and is what
writes the evidence the preconditions read. Tab B gets one secondary
`Run now` shortcut calling the same endpoint, so a user iterating on code need
not change tabs. There is one execution path, two entry points.

# 3. Scope Principle — No New Engines

Every subsystem this workspace requires already exists and is test-pinned. This
is a contract for **wiring and presentation**, not for new subsystems. Nothing
in this document authorises a new capture engine, a new IR format, a new
compiler, a new runner or a new approval workflow.

| Need | Existing implementation | Do not rebuild |
|---|---|---|
| IR entity, readiness, provenance | `automation_ir_drafts` (migration 048) — `contract`, `readiness`, `source_action_ids` | UI-019 created this table explicitly for UI-020 |
| IR schema and validation | `app/agents/automation/generation_contract.py` — `AutomationGenerationContract` | The pydantic model is the schema of record |
| Code rendering | `app/services/script_compiler/` — `compiler.py`, `playwright_renderer.py`, `pytest_renderer.py`, `locator_policy.py` | The compiler is the only thing that renders code |
| Real execution | `app/services/automation_runner/` — `local_playwright.py`, `docker_playwright.py`, `dispatcher.py`, `preflight.py`, `readiness.py`, `workspace.py` | Real subprocesses, not simulation |
| Static validation | `app/services/static_quality_gate.py` + `app/services/automation_intelligence.py` | The gate is the validation engine |
| Confidence scoring | `app/services/automation_confidence_service.py` | Aggregates only; see Section 14.3 for its gating defect |
| Approval workflow | `app/services/automation_suite/lifecycle.py` — submit / request_changes / reject / approve / publish, separation of duty | Reuse, do not fork |
| Inherited context | `app/services/automation_suite/inheritance.py` — `resolve_suite_inheritance` | The only module that queries for evaluation |

**Rationale for stating this so forcefully:** the automation module has been
rebuilt four times. Each rebuild re-decided the data model. The data model is
now settled and pinned by roughly 240 focused tests across UI-018 and UI-019.
The remaining work must sit on top of it.

# 4. Core Domain Model

The workspace operates on **one Automation Suite Member** — the join row in
`automation_suite_test_cases` — and the artifacts hanging off it:

```
AutomationSuite (UI-018)

    │     .contract         : the IR version that produced it

    └── AutomationAssetDecision       ← Tab C writes this (NEW, Section 18)
```

`AutomationSuiteGap` rows and the suite-level conflict findings from UI-018
remain the authority on member readiness. This workspace **reads** them and
**never recomputes** them.

# 5. Source-of-Truth Rules

1. **The test case is the source of truth for behaviour.** Step text is read
   from the test case at render time and never copied into the IR (the rule
   UI-019 already established for `step_key`).
2. **The IR is the source of truth for automation.** Code is derived from it.
   Code is never the input to anything.
3. **The compiler is the only writer of script source.** Per ADR-001, no agent
   and no human persists free-form `.spec.ts` / `.py`. See Section 12.1.
4. **Inherited context is never re-entered.** Application, framework,
   environment and traceability come from
   `inheritance.resolve_suite_inheritance` and render read-only with their
   source label ("Inherited from TC-0008").
5. **UI-018 owns suite status.** This workspace may advance *member* and
   *artifact* state; it must never write `automation_suites.status` except
   through `lifecycle.py`.
6. **Absent data renders as an explained dash, never as `0`.** The
   `unavailable` map pattern from UI-016 / UI-017 / UI-018 applies unchanged.

# 7. Preconditions

To open the workspace the user needs `automation_suite.read` plus project
membership. The subject member must exist and its suite must not be archived.

The workspace **opens even when the member is blocked**. UI-019 established
this precedent deliberately: a member left `BLOCKED` by suite evaluation is an
advisory, not a barrier, because the two common causes ("no automation
classification", "no approved Application Model") are among the things the user
opens the workspace to fix. Blocking entry would be circular.

Blockers are shown in the readiness strip (Section 10), not as a locked door.

# 10. Readiness Strip and the Single Primary Action

Directly below the header, above the tabs. **This is the most important element
in the workspace** and the direct answer to the "too many steps" feedback.

It states, in plain English, exactly one of:

| State | Message | Primary action |
|---|---|---|
| IR incomplete | "3 steps need a locator before this can be automated." | `Resolve 3 steps` → IR Editor tab, filtered |
| IR ready | "Behaviour is complete and validated." | `Compile and dry run` |
| Compiled, not run | "Code generated. Not yet executed." | `Run dry run` |
| Dry run failed | "Dry run failed at step 7 — element not found." | `Open failure` → Script Editor tab, results |
| Gate blocked | "2 blocking validation findings." | `Review findings` → Validation & Review tab |
| **AI Approved** | "AI Approved at 82/100. Awaiting final approval before publish." | `Give final approval` |
| Final approved | "Final approved by <name> on <date>." | `Publish to suite` |
| Published | "Published and frozen in snapshot `<sha8>`." | *(none — immutable)* |

Rules:
- **Exactly one primary button is visible at a time.** Secondary actions live
  in an overflow menu.
- The strip never shows a spinner as its only content. Work in progress shows
  the named stage being executed ("Compiling…", "Running dry run — step 4 of 12").
- When the machine advances the asset by itself, the strip animates the change
  and records it in activity. The user is told what happened, not asked to do it.

# 11. Tab A — IR Editor (UI-020 Automation IR Editor)

## 11.1 What this tab is for

It converts an emitted IR draft into a **validated, complete
`AutomationGenerationContract`**. Its highest-value job — and the thing the
layout must lead with — is **resolving `custom` steps**.

A `custom` step is the emitter's honest TODO: an action with no observed
locator. The compiler renders it as a visible `TODO` comment and never
fabricates a call. Every `custom` step is therefore a hole in the automation,
and the count of them is the single best measure of how far the asset is from
runnable.

**The tab does not open on a JSON tree.** It opens on the work.

## 11.2 Layout

Two columns, as drawn in `UI-020_Automation_IR_Editor.png`: a main editing
column and a right rail. The workspace-subject bar sits above both.

## 11.3 The `readiness` map drives the Unresolved section

`automation_ir_drafts.readiness` already records what the emitter could not
resolve. It is rendered verbatim as the Unresolved list — not recomputed.

**Verified shape** (`services/recorder/ir_emitter.py`, confirmed against live
rows 1, 2 and 4 on 2026-07-30):

```json
{
  "unresolved": [ { "kind": "...", "detail": "...", "<context>_id": 22 } ],
  "unresolved_count": 1,
  "step_count": 2,
  "assertion_count": 1,
  "custom_step_count": 0,
  "ready_for_script_generation": false
}
```

`unresolved[]` entries always carry `kind` and a human-readable `detail`, plus a
context id naming what to open — `action_id`, `checkpoint_id` or `sequence`.
The **ten emitted `kind` values** are:

| `kind` | Meaning |
|---|---|
| `unmapped_action` | recorded action attached to no step |
| `no_locator` | action with no usable locator |
| `navigate_without_url` | navigation with no resolved URL |
| `unbound_input` | a typed literal not classified as test data, secret or runtime value |
| `unreviewed_recommendation` | a recommended checkpoint never reviewed, so not asserted |
| `unrenderable_checkpoint` | checkpoint with no contract representation |
| `checkpoint_without_element` | checkpoint missing its target element |
| `secret_reference` | a value identified as a secret |
| `environment_profile` | environment could not be resolved |
| `script_type` | script type could not be resolved |

Each `kind` maps to one resolution affordance in the Unresolved section. The UI
must handle an unknown `kind` gracefully — render `detail` with a generic
"Open source action" affordance rather than dropping the row.

**`ready_for_script_generation` is not a gate.** The emitter's own comment is
explicit: a draft with open items is still worth producing, and UI-020 is where
they get resolved. It drives the readiness strip's wording, nothing else.

**`custom_step_count` is a separate field from `unresolved_count`** — a draft can
have zero custom steps and still be unready. Section 11.9's exit condition
therefore requires *both* `unresolved` empty and `custom_step_count == 0`.

## 11.4 Editing rules — the validator constraint

`AutomationGenerationContract` enforces `_targets_resolve_to_real_elements` at
`model_validate`. Every step, assertion and UI cleanup target must resolve to a
declared `<PageObject>.<element>` pair. A bare page object, a typo, the literal
`"page"` on a non-URL assertion, or a missing target on an element-required
action all raise.

**This is the primary UX risk of UI-020.** If the tab allows free editing and
validates on save, every save is a 422 and the screen feels broken.

**Editing surface (user decision, Section 2.1.3): structured form by default,
raw JSON behind `Advanced`.** Both surfaces edit the same real contract and
share the `Validate` / `Format` actions, the schema badge and the `Save IR`
footer. The JSON surface is a first-class capability for power users, not a
debug view — but it is never what the tab opens on.

Mandatory design response:

1. **Target is never a text input.** It is a picker over declared elements of
   declared page objects. Typing a target string is impossible.
2. **Action is a select over the closed vocabulary** — `navigate`, `fill`,
   `click`, `check`, `uncheck`, `select`, `hover`, `wait_for_visible`,
   `wait_for_url`, `custom`. Free text is impossible.
3. **The form adapts to the action.** `navigate` takes a raw path, not an
   element. `wait_for_url` matches on `value`. `custom` requires a
   `description`. The element picker only appears for the seven
   element-required actions.
4. **Validate on every edit, not on save.** Round-trip the draft contract
   through `AutomationGenerationContract.model_validate` server-side on change
   (debounced) and surface the **actual pydantic message** inline against the
   offending row.
5. **`name` fields are constrained identifiers.** `PageObject.name` and
   `PageElement.name` must match `^[A-Za-z_][A-Za-z0-9_]{0,63}$` — enforced in
   the input with live feedback, because these become TypeScript class names
   and filesystem path segments. The client-side rule must mirror
   `_SAFE_IDENTIFIER_RE` exactly.
6. **Saving an invalid contract is impossible**, so `automation_ir_drafts.contract`
   never holds a shape the compiler cannot consume.
7. **The `Advanced` JSON surface is validated identically** — same endpoint,
   same pydantic model, same inline errors. It bypasses the pickers, never the
   validator. Switching between form and JSON mid-edit preserves unsaved state.

## 11.5 Element sourcing

The element picker is populated from the approved Application Model (UI-016)
for the inherited application, plus elements already declared on the draft. An
element observed during recording but not present in the Application Model is
offered with a "recorded, not in model" label and a link to propose it into the
model — never silently promoted.

## 11.6 Data bindings

`TestDataBinding` entries render with their `${placeholder}` and resolve via
`app/services/parameter_binding.py`. The tab must make it structurally
difficult to inline a literal where a binding belongs: any step `value`
matching a credential-like or PII-like pattern raises an inline warning
pointing at "bind this to test data instead". This mirrors the hardcoded-data
rule the static gate already enforces downstream — surfaced here, where it is
cheap to fix, instead of at validation, where it is a rejection.

## 11.7 Provenance

`source_action_ids` links every IR step to the observed recorder action that
produced it. Each step exposes "Show source" → a drawer with the recorded
action, its captured evidence and its network context (reusing UI-019's
`DiscoveryAction` / `DiscoveryCapture` and UI-017's parser). A step with no
source action is labelled "authored", not left ambiguous.

## 11.8 Versioning

Editing a `DRAFT` IR edits it in place. Editing an IR that has already produced
a script creates version n+1 and marks the prior `is_current = false`
(`IR_DRAFT_STATUSES` = `DRAFT` | `SUPERSEDED`). The version chain is visible
with a diff between any two versions.

## 11.9 Exit condition

The IR Editor tab is complete when: the contract validates, `readiness` is
empty, and there are **zero `custom` steps**. At that point the asset
auto-advances to Script Editor (Section 15).

# 12. Tab B — Script Editor (UI-021)

## 12.1 The defining constraint — this is not an editable code editor

**ADR-001 forbids persisting free-form script source.** The compiler is the
only renderer, and `static_quality_gate.py` *enforces* it:
`_check_generation_header` hard-blocks any script missing the
`GENERATED BY nxtQA Script Compiler` marker, and `_check_tc_req_mapping`
hard-blocks any script missing its Test Case / Requirement header.

A hand-edited file loses or invalidates that header and is rejected by the
platform's own gate. **Building a save-capable text editor here would put the
screen in permanent conflict with the gate and would constitute rebuild #5.**

Therefore UI-021 is:

- **Read-only, syntax-highlighted code** with full file-tree navigation over
  `compiled_files`
- **"Edit behaviour"** as the only path to changing code — deep-links to the
  IR Editor tab at the IR construct that produced the selected line
- **Compile / recompile** as an explicit action
- **Dry run** against the real runner
- **Accepted-exception management** for gate findings
- **Diff** between script versions

The tab states this plainly in the UI: *"Code is generated from behaviour and
cannot be edited directly. Edit the behaviour to change the code."* Users must
understand this as a governance guarantee (every line is traceable to a
validated contract), not as a missing feature.

## 12.2 Layout

## 12.3 Compile

Calls the existing compiler against the current IR draft. On success it writes
a new `AutomationScript` row — never an in-place mutation, per the ADR-001
rollback guarantee already implemented via `parent_script_id` / `version`.
`contract` on the new row records the exact IR that produced it.

Compilation failure is surfaced with the compiler's real error and a deep link
back to the responsible IR construct.

## 12.4 Dry run

Dispatches through `automation_runner/dispatcher.py` to the configured runner
(`local` subprocess or Docker, per `config.py`). Preflight and readiness checks
run first and their real reasons are shown when they refuse.

Results render as a step-by-step timeline with pass/fail per step, duration,
console output and stderr. Where the runner produces artefacts, they are
linked. **Video and trace are not claimed** unless the configured runner
genuinely produces them — the Playwright-MCP limitation UI-019 documented still
applies to the recorder path.

Each dry run is recorded as an `ExecutionResult` with
`metadata_.automation_script_id` and `metadata_.dry_run = true`, which is
already the shape `automation_confidence_service._dry_run_stability` reads.
This wiring is what turns that dimension from a neutral 0.5 into real evidence.

**Verified 2026-07-30 inside `stlc_worker`.** `LocalPlaywrightRunner.run()`
executed a compiled bundle end to end: `exit_code 0`, 1.32s, one per-test result
with status `pass`, `run.log` written to the workspace.

Two facts the implementation must not get wrong:

- **`run_status` on success is `"completed"`, not `"passed"`.** The per-test
  verdict lives on the individual `PerTestResult.status` (`pass` / `fail` /
  `skip` / `error`, mapped from Playwright by `PLAYWRIGHT_STATUS_TO_DB`).
  Treating `run_status` as the pass/fail signal would mark every successful run
  as not-passed and permanently starve precondition 4.
- **Attachments came back empty** in the worker run while a direct host run of
  the same bundle produced three. Attachment capture depends on the generated
  `playwright.config.ts` (`write_playwright_config`), not on the runner. Section
  22's "video and trace are not claimed" therefore stands: evidence links render
  only when the run actually produced them.

## 12.5 Provenance

Every rendered line traces to its IR construct. Selecting a line highlights the
originating step / element / assertion and offers "Edit behaviour".

## 12.6 Exit condition

The Script Editor tab is complete when a compile has succeeded and at least
**one dry run has passed** (Section 14.4, tunable). The asset then auto-advances
to Validation & Review.

Rendered directly from `static_gate_result` — `violations` (block) and
`warnings` (warn), each with its `code` and real message. The gate already
combines:
- the `automation_intelligence` rule engine (hard waits, weak locators, missing
  assertions, hardcoded data and credentials), where `high` severity blocks
- the ADR-001 header and TC/REQ mapping checks
- the optional `npx playwright test --list` syntax check

**`syntax_check` must be rendered as one of three states, never two.** It
returns `"skipped"` when `npx` is unavailable on the host. A skipped syntax
check must display as *"Syntax check skipped — Node/Playwright not available on
this host"*, never as a pass. Presenting a skipped check as green would report
a verification that did not happen.

**Operational prerequisite — VERIFIED 2026-07-30 (Day 1).**

`backend/Dockerfile` installs Node 20, `@playwright/test@1.44.0` and Chromium
into the worker image, and `docker-compose.yml` runs the worker from that image.
The runner and the gate execute there, so `npx` **is** available in production
and `_syntax_check` genuinely runs rather than skipping.

**On a Windows developer host it does not**, and this is a real limitation to
know about rather than a defect to fix in this pass:
`static_quality_gate._syntax_check`, `preflight._detect_playwright` and
`workspace._npm_global_root` all invoke `npx` / `npm` through `subprocess`
without `shell=True`, and Windows requires the `.cmd` extension. All three
degrade honestly — `syntax_check` returns `"skipped"` with
`[WinError 2] The system cannot find the file specified`, preflight reports
"@playwright/test is not installed", and `write_playwright_config` logs
"npm not found while resolving global module root" and creates no
`node_modules` link. Nothing crashes and nothing reports a false pass, which is
exactly why Section 13.3 requires `skipped` to render as its own third state.

Consequence for implementation: **dry runs must be exercised inside the worker
container, not against a Windows host.** A developer running the backend
natively on Windows will see every script marked unrunnable with an accurate
reason.

## 13.4 Accepted exceptions

A warning may be accepted as an exception, appending its `kind` to
`script.metadata_["static_gate_exceptions"]` — the mechanism the gate already
honours. Accepting an exception is a **governance action**, permissioned under
`APPROVE_TEST_CASES`, not `GENERATE_AUTOMATION`, following the precedent UI-018
set for `approve_exception`. Every acceptance records actor, timestamp and
reason.

Blocking violations cannot be excepted from this screen.

## 13.5 Final approval

The one governed human gate. Enforces:
- **Separation of duty** — the identity that generated or last edited the asset
  cannot give final approval. Reuse the existing check that produces
  `SEPARATION_OF_DUTY_VIOLATION`; do not write a second one.
- **No blocking findings** — mirrors `_require_no_blocking_criticals`.
- **Reason required on reject**, recorded into review history.

# 14. The Autonomy and Scoring Model

This section is normative for all three tabs.

## 14.1 Two independent axes — never one field

`AI_APPROVED` must **not** be a value of the field a human writes. If the
machine both generates and approves on the same axis, it is committing the very
separation-of-duty violation `lifecycle.py` already refuses for humans.

| Field | Owner | Values |
|---|---|---|
| `autonomy_state` | machine | `AI_PENDING` · `AI_HELD` · `AI_APPROVED` |
| `approval_state` | human | `PENDING_FINAL` · `FINAL_APPROVED` · `REJECTED` |

`autonomy_state` advances the pipeline. `approval_state` remains an
unforgeable human record. They are never the same column.

**How this maps onto the reference image's approval stepper.** The drawn
stepper — Draft → Pending Review → Changes Requested → Approved → Published —
is the **human axis** and is retained exactly, because it mirrors `lifecycle.py`
and reads consistently with UI-016 and UI-018. `AI_APPROVED` is **not** added as
a stepper node; doing so would put the machine's verdict and the human's record
on one axis, which is the violation this section exists to prevent. The machine
axis is rendered as the gating panel (Section 13.2) and the header badge
(Section 9). What autonomy does to the stepper is *move the asset along it* —
a qualifying asset arrives at `Pending Review` on its own.

## 14.2 The gate is two-part — preconditions before score

```
AI_APPROVED  ⟸  ALL hard preconditions met  AND  score ≥ threshold
```

Hard preconditions for the automation stages, all computable today:

| # | Precondition | Source |
|---|---|---|
| 1 | Static gate passed, **zero** blocking violations | `static_gate_result.passed` |
| 2 | **Zero `custom` steps** in the IR | contract `steps` |
| 3 | Locators grounded against an approved Application Model | `LocatorMapEntry` rows actually exist for the referenced elements |
| 4 | ≥ N passing dry runs recorded | `ExecutionResult` with `dry_run = true` |
| 5 | No unwaived critical suite gaps for this member | `automation_suite_gaps` |

Preconditions 3 and 4 exist specifically to defeat the defect in 14.3.

## 14.3 Why score alone is unsafe — a defect that must be fixed

`automation_confidence_service.py` returns **neutral defaults when evidence is
absent**:

| Dimension | Value when there is no evidence |
|---|---|
| `_locator_confidence` | **0.5** (no grounded locators) |
| `_dry_run_stability` | **0.5** (no dry-run history — commented "neutral, not penalized") |
| `_environment_readiness` | 0.5 (no resolvable URL) |
| `_data_readiness` | **0.7** (no test data on the test case) |

Those defaults are correct for **display** and dangerous for **gating**. Worked
example — a script never executed once, with a clean static gate and test data
present:

```
locator 0.5×0.2 + assertion 1.0×0.2 + data 1.0×0.2 + env 0.5×0.2 + dryrun 0.5×0.2
= 0.10 + 0.20 + 0.20 + 0.10 + 0.10 = 0.70
```

and with partially grounded locators it clears 0.75 **on an evidence base of
essentially nothing**. The composite currently conflates *"this is good"* with
*"we do not know"*. A threshold-only gate would systematically auto-approve the
least-evidenced assets — the exact inverse of the intent.

The preconditions in 14.2 are the fix. **The score discriminates among
qualified candidates; it never certifies an unqualified one.** The scoring
service itself is not modified — its neutral defaults stay correct for display.

## 14.4 Thresholds and tunables

| Parameter | Value this pass | Note |
|---|---|---|
| `AUTOMATION_AI_APPROVAL_THRESHOLD` | **80** / 100 | Config-only |
| `AUTOMATION_MIN_PASSING_DRY_RUNS` | **1** | *Stated assumption — user has not confirmed. Set to 1 because there is no run history to tune against yet; raise once real history exists.* |
| Rubric id | `automation.v1` | Recorded on every decision |

**Per-stage rubrics, not one universal number.** Requirement quality, test-case
quality and automation confidence rest on different evidence bases; a single 75
across all of them would be arbitrary. The *shape* is shared (0–100 +
dimensions + preconditions + rubric id); the *rubric* is per stage. Only
`automation.v1` is defined in this pass (Section 22).

**No threshold administration UI.** Configurable autonomy policy is UI-055
(Phase 3). Thresholds live in config and render read-only here as
"Threshold: 80 (project policy)".

## 14.5 The decision record — snapshot, never a pointer

Every autonomy decision persists, immutably:

- score and full dimension breakdown **as computed at decision time**
- every precondition and whether it was met
- rubric id and threshold **value** (not a reference to current config)
- model / prompt versions in play
- timestamp and triggering event

Thresholds and rubrics will change. A pointer to current config cannot answer
*"why was this approved"* six months later. Store the values.

## 14.6 Interaction with `WORKFLOW_OWNED_STATUSES` — a known trap

UI-018 Phase B already hit and solved this: once a suite is in review, approved
or published, re-evaluation refreshes its rollup and findings but **must not
recompute its status**, or the next evaluation pass silently undoes an
approval.

The same rule binds autonomy. **Once `approval_state` leaves `PENDING_FINAL`,
autonomy re-evaluation may refresh the score for display but must never change
`autonomy_state` or reopen the decision.** Reuse the existing
`WORKFLOW_OWNED_STATUSES` guard; do not write a parallel one.

# 15. Stage Advancement Rules

Automatic, deterministic, and always visible in activity.

| From | Condition | To | Actor |
|---|---|---|---|
| IR Editor | contract validates · `readiness` empty · zero `custom` steps | Script Editor | machine |
| Script Editor | compile succeeds | Script Editor (compiled) | machine |
| Script Editor | ≥ N dry runs passed | Validation & Review | machine |
| Validation & Review | all preconditions met AND score ≥ threshold | `autonomy_state = AI_APPROVED`, workflow advances to `Pending Review` | machine |
| Validation & Review | preconditions unmet OR score < threshold | `autonomy_state = AI_HELD` | machine |
| Validation & Review | human decision | `approval_state = FINAL_APPROVED` / `REJECTED` | human |

**A healthy asset requires zero clicks to reach final review.** That is the
measurable objective of this contract, and the reason the reference images'
"eligible for Submit" model was not adopted (Section 2.1.5). The `Submit for
review` control is retained as a **fallback** for assets the machine has held,
never as a required step on a qualifying asset.

Every automatic advancement writes an activity row naming the rule that fired
and the evidence. Nothing advances invisibly. Manual advancement remains
available to authorised roles as a fallback control, always recorded as an
override with a reason.

`AI_HELD` is never a dead end: the readiness strip states the specific
unsatisfied precondition or the weakest dimension and links to the tab that
fixes it.

# 16. The Hard Line — Where Final Approval Becomes Mandatory

**Confirmed by the user: publish / production execution.**

An `AI_APPROVED` asset flows freely through IR → compile → dry run →
validation. It **cannot** cross either of these without `FINAL_APPROVED`:

1. **Publish** — inclusion in an `AutomationSuiteSnapshot`. UI-018 already makes
   publication the freezing event, with a sha256 over a canonical payload and
   409 `SUITE_IMMUTABLE` on every subsequent mutation. Everything before this is
   reversible; this is not.
2. **Execution against `PROD_SANITY`.**

Backstops, required because deferred review otherwise accumulates invisibly:

- **Final rejection cascades.** Rejecting an `AI_APPROVED` asset marks
  downstream artifacts as requiring re-review, or the deferral creates silent
  drift.
- **Aging is visible.** A "Pending final approval" queue on the Suite Detail
  Overview, with counts and age buckets, so unreviewed AI approvals are a number
  on a screen rather than an invisible backlog.
- **Publish preflight enumerates** every member still lacking final approval and
  refuses with that list.
